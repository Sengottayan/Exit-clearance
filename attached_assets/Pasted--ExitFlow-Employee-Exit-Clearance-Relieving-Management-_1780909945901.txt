# ExitFlow — Employee Exit Clearance & Relieving Management System
## Complete Bolt AI Build Specification (v2)

---

## WHAT YOU ARE BUILDING

**ExitFlow** is a production-grade internal HR platform for IT companies to manage the complete employee exit lifecycle — from resignation to issuing the final relieving letter. It is a single Next.js application with a public landing page, a unified login, and role-based routing that takes each user directly into their relevant workspace after authentication.

This is NOT a collection of separate portals stitched together. It is ONE application that adapts its navigation, dashboard, and available actions based on who is logged in. Think of how Linear or Notion handles different user roles — one URL, one product, different experiences.

---

## CORE PRINCIPLES (READ BEFORE BUILDING ANYTHING)

1. **Single entry point**: The app lives at `/`. Public homepage → login → role-based redirect. No separate `/employee`, `/manager`, `/hr` portal URLs visible to the user. After login, everyone lands at `/dashboard` and the app renders what is appropriate for their role.

2. **Role-aware, not role-separated**: The sidebar, dashboard content, available nav links, and page actions all adapt to the logged-in role. The URL structure is clean (`/dashboard`, `/cases`, `/cases/[id]`, `/tasks`, `/settings`) — not cluttered with role prefixes.

3. **Mobile-first, desktop-optimised**: Design for 375px width first, then scale up. The sidebar collapses to a bottom nav bar on mobile.

4. **Contextual, not exhaustive**: Every screen shows only what the current user needs right now. No overwhelming grids of options. One primary action per page, secondary actions tucked in menus.

5. **Data-ink ratio**: Every pixel earns its place. No decorative banners, no empty carousels, no lorem ipsum cards. If there is no data, show a meaningful empty state with a clear next action.

### Post-Login Redirect Logic
```typescript
// After successful login, redirect based on role:
const ROLE_REDIRECT: Record<Role, string> = {
  employee:      '/dashboard',   // sees own exit status
  manager:       '/dashboard',   // sees team exit list
  hr:            '/dashboard',   // sees ops overview
  dept_approver: '/dashboard',   // sees their pending tasks
  admin:         '/dashboard',   // sees system overview
}
// Always /dashboard — the dashboard component renders the correct view
```

### Route Protection
Create `middleware.ts` at project root:
- If unauthenticated → redirect to `/login`
- If authenticated but wrong role for route → redirect to `/dashboard`
- Public routes: `/`, `/login`

## DASHBOARD PAGE — `/dashboard` (role-aware)

This is one page file (`app/(app)/dashboard/page.tsx`) that renders different content based on the authenticated user's role. Use a `DashboardRouter` component that reads the role from the Zustand store and renders the correct dashboard view.

```typescript
// app/(app)/dashboard/page.tsx
export default function DashboardPage() {
  const { user } = useAuthStore()
  
  if (user.role === 'employee')      return <EmployeeDashboard />
  if (user.role === 'manager')       return <ManagerDashboard />
  if (user.role === 'hr')            return <HRDashboard />
  if (user.role === 'dept_approver') return <DeptApproverDashboard />
  if (user.role === 'admin')         return <AdminDashboard />
}
```

### Page Header (shared across all dashboard views)
```
Left: "Good morning, [First Name] 👋" (h1 text-page)
      "[Role label] · [Department]" (text-muted text-sm)
Right: [role-specific primary CTA button]
```

## SHARED COMPONENTS (`components/shared/`)

### `<StatusBadge status={} size="sm|md" />`
Maps status string → label + dot color + bg color. All status values:
`pending` · `in_progress` · `approved` · `rejected` · `overdue` · `completed` · `cancelled`
Renders as: `<span className="inline-flex items-center gap-1.5 rounded-full px-2.5 py-0.5 text-xs font-medium" style={{ background: bgColor, color: textColor }}><span className="w-1.5 h-1.5 rounded-full" style={{ background: dotColor }}/>{label}</span>`

### `<SLARiskChip dueAt={string} />`
Calculates time remaining using date-fns `differenceInHours(dueAt, now)`.
- `> 24h`: green "On Track"
- `1–24h`: amber "Due Today" or "Due in Xh"
- `0`: amber "Due Now"
- `< 0`: red "Overdue by Xd Xh"

### `<ClearanceProgressBar tasks={ClearanceTask[]} />`
Segmented bar showing proportions. Segments: green (approved) · blue (in_progress) · gray (pending) · red (rejected)
Below bar: "5 of 8 approved" label

### `<UserAvatar name={string} size="sm|md|lg" />`
Renders colored circle with initials. Hash the name to pick a consistent color from a palette of 8 colors.

### `<PageHeader title breadcrumb actions />`
Sticky top-of-content header. Left: breadcrumb (text-muted) above title (h1). Right: action buttons.

### `<EmptyState icon title description action? />`
Centered layout: Lucide icon (48px, muted) + title + description paragraph + optional CTA button.

### `<ConfirmDialog title description confirmLabel confirmVariant onConfirm />`
Shadcn Dialog wrapper for all destructive confirmations.

### `<DataTable columns data filters? pagination? />`
Generic typed table component. Shadcn Table underneath. Supports: sortable columns (click header), filter tabs, pagination (20/page), bulk checkbox selection, empty state.

## KEY BUSINESS RULES (enforce these in the UI)

1. **Relieving Letter is locked** until every mandatory department's task status is `approved`. The generate button must be `disabled` with a Shadcn Tooltip: "Waiting for: IT, Finance (2 departments pending)".

2. **Approve Clearance button is locked** until every checklist item where `isMandatory: true` is checked. Show inline validation (amber highlight on unchecked required rows) when user tries to approve without completing.

3. **SLA chip is always live-calculated** from `slaDueAt` vs `Date.now()` — never hardcoded strings. Use a `useSLA(dueAt)` hook that returns `{ status, label, color }`.

4. **Employee cannot access `/resign`** if they already have a case in the store. Middleware redirects them to `/dashboard`.

5. **Rejection cascade**: When a task is rejected, the exit case status must show a warning state on the HR dashboard and case detail. HR must re-open the task for the original assignee to re-do it.

6. **Manager approval gate**: All clearance tasks remain in `pending` state until the manager first approves the resignation. Task cards show "Waiting for manager approval" if case status is `pending_manager`.

7. **New case Step 3**: Mandatory departments show a `Lock` icon with no toggle. Hovering shows tooltip: "This department is required and cannot be skipped." Non-mandatory depts show a working toggle switch.
